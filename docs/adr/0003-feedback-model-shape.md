# Feedback model shape

Guest feedback submitted via a **QR link** (`/scan/{token}`) is stored per-location and attributed to the **QR code** that was scanned: required `Feedback.QrCodeId` → `QrCode`, which belongs to a `RestaurantLocation`. The `Feedback` table has no `RestaurantId` column — the restaurant is reached via `RestaurantLocation.RestaurantId` when needed. **QR type** is not denormalized on Feedback; join `QrCode` when source labels are needed. Paused or Archived codes keep historical FKs but reject new scans.

The form captures three required text fields: guest name, guest contact (a single string holding either an email or a phone number, guest's choice), and a comment. It also captures `OffersOptOut`, a boolean that defaults to `false`; the pre-checked UI is mapped so unticking records `true`. A `ContactType` column (`Email` | `Phone` | `Unknown`) records a heuristic classification of the contact string at submission time, so future operator-reply features know which channel to use without re-parsing.

We rejected separate `GuestEmail` and `GuestPhone` columns because the form has a single contact field and forcing the guest to choose a channel adds friction. We rejected a per-restaurant FK because guest entry is per–QR code / location — attribution must follow the scanned token, not the restaurant — and per-location feedback is what the per-location dashboard needs to display. We rejected storing only `RestaurantLocationId` without `QrCodeId` once multiple QR codes per location exist (see [ADR-0020](0020-per-location-qr-codes-opaque-tokens.md)).
