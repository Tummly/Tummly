# Per-location Capture loads via Capture location snapshot

Per-location Capture body data loads through one **Capture location snapshot** read (`GET /api/capture/locations/{locationId}/snapshot`) instead of parallel `GET /api/capture/performance` and `GET /api/capture/placements`. A shared windowed engagement aggregate kernel backs the snapshot and **Capture overview** (via the **Capture multi-location reads module**); current location KPI totals are the sum of Active/Paused **QR code** rows from one current-window group-by, with previous-period counts at location grain only. The Operator Capture page module uses one load status for the body. We deleted the two old GETs rather than keeping thin shims. We rejected client-side summing of current KPIs from placement rows alone (totals can drift when tables split digital vs catalog). We rejected dual progressive load statuses once there is a single HTTP read. Location performance list composition stays on ADR-0021; Multi Preview lean read is ADR-0023 (**Capture preview-options**); QR lifecycle extraction stays a separate seam. ADR-0022’s interim “Multi Preview may over-fetch snapshot KPIs” is superseded by ADR-0023.
