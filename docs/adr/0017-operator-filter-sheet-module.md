# Operator filter sheet is one kernel, per-surface schema adapters

Guests, Guest Activity, and Guest Feedbacks each hand-rolled a filter dialog: separate `FiltersDialog` components, separate `*FilterSelection` modules (applied/pending state, chip projection, date-preset math, location-scope stepping), and — only for Guests — a different footer (no unified Cancel/Apply). The three copies drifted in small ways (chip id formats, location "clear on shell change" behaviour, date validation) and every new filterable field meant re-deriving the same session bookkeeping a third time.

We extract a single, domain-agnostic session kernel at `src/lib/operatorFilterSheet/` that owns applied vs. pending selection, dirty-Apply detection, chip projection/removal, and the `date` / `location-scope` picker steps. Each surface supplies a declarative `FilterSheetSchema` (field id, kind, label, options/axis/preset labels) and the kernel derives everything else — including the chip id/kind conventions that were previously duplicated by hand. One React adapter, `OperatorFilterSheetDialog` (`src/components/dashboard/operator/FilterSheet/`), renders any schema and always exposes the same footer: **Clear all** on the left, **Cancel** / **Apply** on the right, where **Apply commits pending → applied without closing the dialog**. Guests adopts this Profile-established footer pattern instead of the reverse. Query-param builders (`guestsListQueryParams`, `guestActivityListQueryParams`, `guestFeedbacksListQueryParams`) stay in their domain libs and read the kernel's `OperatorFilterSelection` via small typed helpers (`getMultiSelectIds`, `getDateValue`, `getLocationOverride`) — they do not move into the kernel, since query-shape mapping is domain knowledge, not session bookkeeping.

We migrated all three surfaces in one change rather than adding a fourth parallel implementation alongside the kernel: a partial migration would leave two competing filter-dialog patterns live at once, which is exactly the drift this ADR removes. We rejected making the kernel own field option catalogs/labels — those are domain data (`MARKETING_LABELS`, `ACTIVITY_TYPE_OPTIONS`, tag catalogs) that differ per surface and belong in the schema adapters, not the session module. We rejected unit-testing the dialog's React internals; the seam worth testing rigorously is the kernel's public interface (session lifecycle, multi-select toggle, date with/without axis, location-scope stepping, chip project/remove), which is pure and framework-free.

## Consequences

- Adding a filterable field to any surface is a schema edit (`*FilterSheetSchema.ts`), not a new dialog or a new selection-state module.
- Chip id/kind conventions (`marketing:eligible`, `location:2`, `location:all`→`location-all`, fixed `date` id) are now enforced by `chips.ts` for every surface, not re-typed per dialog.
- The Activity tab's filter grid is now the same 2-column layout as Guests/Feedbacks instead of a stacked single column — a deliberate, minor UX delta in exchange for one dialog implementation.
- Apply commits pending → applied and keeps the sheet open (Cancel / dismiss closes). Page and tab modules re-sync `filtersSession` via `openSession(applied)` instead of nulling it.
- `docs/adr/0016`'s SQL-composed Guests filters are untouched; this ADR only changes how the frontend assembles the selection that `guestsListQueryParams` turns into query params.
- Out of scope: ADR-0014's shared tabs/spinner/empty-state extraction, and any rewrite of the list/tab modules beyond wiring them to the new session/chip APIs.
