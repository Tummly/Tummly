# Feedback AI classification: Pending rows are the durable queue

Async **AI classification** durability uses `ClassificationStatus = Pending` on Feedback as the source of truth for outstanding work — not a separate outbox/jobs table, and not the in-memory Channel. Workers soft-claim Pending rows (claim timestamp + timed lease + per-row claim attempt budget), then write terminal **Succeeded** or **Failed**. The product lifecycle stays `Pending → Succeeded | Failed`; there is no operator-visible `Processing` status. The Channel remains a wake-up hint only: submit still enqueues an id for low latency, but correctness survives process restart via startup sweep plus a ~30s poll that reclaims unclaimed or lease-expired Pending rows. Provider HTTP retries (`MaxAttempts`) stay separate from row claim attempts (`MaxClaimAttempts`); exhausting claim attempts marks the same generic **Failed** (clear sentiment/issues, publish the thin Feedback/Home terminal signal). Degree of parallelism is configurable and defaults to 1.

We rejected a separate outbox (second concept beside the lifecycle already on Feedback), a `Processing` status (API/UI/glossary churn for a state operators never need), and Channel-as-primary with startup-only requeue (Channel drop mid-run would wait until the next restart). This ADR does **not** add a SignalR backplane: live `Clients.User` fan-out for Notifications and Feedback/Home assumes a **single backend instance** (or an explicit future backplane). Reopen if multi-instance deploy is required without a backplane, if claim/lease semantics prove too heavy for the Feedback row, or if classification work must leave the Feedback aggregate.

**Module surface:** `IFeedbackClassificationWork` — `NotifyAsync` (wake), `RunAsync` (hosted loop), `DrainAsync` (same path for tests). Soft-claim columns `ClassificationClaimedAt` / `ClassificationClaimAttempts` are implementation detail, not product lifecycle.

**Failure policy (terminal-or-bust where writable):** After a successful soft-claim, provider results and post-provider logic/mapping errors that can still be written become terminal **Failed** (or **Succeeded**) immediately — not left Pending for the outer catch to drop. `SaveChanges` / DB failures while writing that terminal row stay retryable via lease reclaim and `MaxClaimAttempts` (we cannot invent Failed if the database will not accept writes). SignalR publish after a successful terminal persist is best-effort: publish failures are logged and never reopen or flip classification; REST catch-up remains the recovery path for missed live events.
